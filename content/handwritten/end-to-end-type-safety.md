# End-to-End Type Safety

## 1. Creating Schema and Types
* Create a folder in the root of the Next.js application & define the schema there[cite: 7].
* Example:
  ```javascript
  export const ProductSchema = z.object({
      name: z.string(),
      description: z.string(),
      price: z.number()
  });
  
  export type Product = z.infer<typeof ProductSchema>;
  ```[cite: 7]
* So we are exporting two things from here:
  1. `ProductSchema` (for Zod validation)[cite: 7]
  2. `type Product` (for TypeScript types)[cite: 7]

---

## 2. In Backend :-
* We can validate the incoming request data before adding it to the database[cite: 7].
  `ValidatedData = ProductSchema.parse(req.body)`[cite: 7]
* We can also trim the data if there are unnecessary extra data incoming[cite: 7].
  `trimmedData = ProductSchema.parse(req.body)`[cite: 7]

---

## 3. In Frontend :-
* We can trim/validate the data before sending it in the API req, just as above[cite: 7].
* ```javascript
  const [formData, setFormData] = useState<Product>()
  ```[cite: 7, 8]

---

## What is the difference between Schema & Types?
* **Schema** -> For Zod validation (of data)[cite: 10].
* **Types** -> For TypeScript (Type suggestion & recommended errors)[cite: 10].

---

## Complete Workflow of Schema, Types & Prisma-types :-

1. First we define the model in our `prisma.schema` for example `Product model`, and Prisma will give you types of each model[cite: 10].
   ```typescript
   type Product = {
       id: string,
       name: string,
       description: string,
       price: number,
       createdAt: Date,
       updatedAt: Date
   }
   ```[cite: 10]

2. Now to put something in database we need data from user/form. And maybe user didn't write the expected field property like wrong email structure, less-digits etc., so we need to show some error first[cite: 10].
   * To show error we need to validate it using Zod[cite: 10].
   * And to validate we need a Zod schema[cite: 10].
   
   ```javascript
   import { z } from "zod";
   
   export const ProductSchema = z.object({
       name: z.string(),
       description: z.string().min(1),
       price: z.number()
   });
   ```[cite: 10]
   * We can use custom validation like:
     `ValidatedFormData = ProductSchema.parse(formData)`[cite: 10]
   * Or we can use `react-hook-form` (Recommended) -> `zodResolver(ProductSchema)`[cite: 10].

3. Now we have correct form-validated data from the form, & we can send it to the api req., which will be handled on route handler/controller[cite: 11].
   * Let's say we send the data from our frontend to backend using axios[cite: 11]:
     `axios.post("/product", { name, description, price })`[cite: 11]
   * On backend we will get the data:
     `dataFromFrontend = req.body`[cite: 11]
   * But here we need to again verify this data, because some hacker may send the req. to backend directly by bypassing the form validation using Postman[cite: 11]!
     `ValidatedData = ProductSchema.parse(dataFromFrontend)`[cite: 11]
   * Now this data will be sent in db req.[cite: 11]
   * But in some case db may need some extra data, like `id`, `role` or some default input, so we must add it in here[cite: 11]:
     `prisma.product.create({ data: { ...ValidatedData, id, role: "user" } })`[cite: 11]
   * But on our case we have `id`, `createdAt`, `updatedAt` handled by Prisma itself so we don't need to specify them[cite: 11].

4. `const res = await product.create(ValidatedData)`[cite: 12]
   * But what will be the type of this `res`?
     It will be `{ id, name, description, createdAt, updatedAt }`[cite: 12]
   * And this is usually what will be sent to the frontend[cite: 12].
   * `NextResponse.json(res)`[cite: 12]
   * This will be received on the frontend as the API call result[cite: 12]:
     `const apiResponse = await axios.post("/product", { ... })`
     `res = await apiResponse.json()`
     `-> { id, name, description, createdAt, updatedAt }`[cite: 12]
   * But frontend doesn't know about its type at runtime. So now to define its type -> **using the types generated by Prisma**:
     `import { Product } from "@prisma/client"`[cite: 12]

---

## But where is Types in all this?
* Types is basically for TypeScript. When application is not running, there is no exchange of information between frontend, backend, DB, but we are defining a lot of variables here and there[cite: 13].
* TypeScript want to know the types of all variables. So we must define (static types) for them[cite: 13].

### There are two kind of types:
1. **Types of database / api response** which contains (`id`, `name`, `price`, `description`, `createdAt`, `updatedAt`)[cite: 13]
   => `import { Product } from "@prisma/client"`[cite: 13]
2. **Types of input fields** (`name`, `description`, `price`)[cite: 13]
   => `export type ProductInput = z.infer<typeof ProductSchema>`[cite: 13]

And now we can use these two everywhere in our application:
1. **Frontend form submission :-**
   `const handleSubmit = (data: ProductInput) => {}`[cite: 13]
2. **Backend api handler :-**
   ```javascript
   router.post("/product", async (req, res) => {
       const input = req.body;
       // req.body doesn't have a type so we may need to define a type here:
       // input: ProductInput
   })
   ```[cite: 13]
