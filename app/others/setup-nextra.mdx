# Setting Up Nextra on a Next.js 16 Project

A step-by-step walkthrough of everything it took to scaffold a **Next.js 16** project and wire in **Nextra 4** as a documentation framework — including the Zod v4 bug we hit and how we fixed it.

---

## 1. Scaffold with `create-next-app`

Everything started with the standard Next.js scaffolding tool:

```bash
npx create-next-app@latest .
```

This generated the initial project with the following structure:

```
remit/
├── app/
│   ├── layout.tsx        # Default Next.js root layout
│   ├── page.tsx          # Default home page (deleted later)
│   ├── globals.css
│   └── favicon.ico
├── next.config.ts        # Minimal Next.js config
├── package.json
├── tsconfig.json
└── ...
```

The default `layout.tsx` used Geist fonts from `next/font/google` and a plain `<body>` wrapper. The `next.config.ts` was empty — just `export default {}`.

---

## 2. Install Nextra and its Docs Theme

Nextra is installed as two packages: the core library and the docs theme.

```bash
bun add nextra nextra-theme-docs
```

This added to `package.json`:

```json
"nextra": "^4.6.1",
"nextra-theme-docs": "^4.6.1"
```

Nextra internally requires `zod ^4.1.12`, so Zod was also installed explicitly to lock the version:

```bash
bun add zod@4.3.6
```

---

## 3. Create `mdx-components.tsx`

Nextra requires a `mdx-components.tsx` file at the root of your project. This file tells Next.js which React components to use when rendering MDX content. It merges Nextra's built-in theme components with any custom ones you define:

```tsx
// mdx-components.tsx
import { useMDXComponents as getThemeComponents } from 'nextra-theme-docs'

const themeComponents = getThemeComponents()

export function useMDXComponents(components: any) {
  return {
    ...themeComponents,
    ...components,
  }
}
```

---

## 4. Update `next.config.ts`

The plain Next.js config was replaced with a Nextra-wrapped config. Nextra wraps the Next.js config using a higher-order function (`withNextra`). The `turbopack.resolveAlias` is required so Turbopack can find the MDX component registry:

```diff
- import type { NextConfig } from "next"
- const nextConfig: NextConfig = {}
- export default nextConfig

+ import nextra from 'nextra'
+
+ const withNextra = nextra({})
+
+ export default withNextra({
+   turbopack: {
+     resolveAlias: {
+       'next-mdx-import-source-file': './mdx-components.tsx',
+     },
+   },
+ })
```

---

## 5. Replace `app/layout.tsx`

The default Next.js layout was completely replaced with Nextra's `Layout`, `Navbar`, and `Footer` components. The `getPageMap()` utility auto-discovers all your `.mdx` pages and builds the sidebar navigation:

```diff
- import type { Metadata } from "next"
- import { Geist, Geist_Mono } from "next/font/google"
- import "./globals.css"
-
- export default function RootLayout({ children }) {
-   return (
-     <html lang="en" className={`${geistSans.variable} ...`}>
-       <body className="min-h-full flex flex-col">{children}</body>
-     </html>
-   )
- }

+ import { Layout, Navbar, Footer } from 'nextra-theme-docs'
+ import { Head } from 'nextra/components'
+ import { getPageMap } from 'nextra/page-map'
+ import 'nextra-theme-docs/style.css'
+
+ export const metadata = {
+   title: 'Remit',
+   description: 'Remit documentation',
+ }
+
+ export default async function RootLayout({ children }) {
+   return (
+     <html lang="en" suppressHydrationWarning>
+       <Head />
+       <body>
+         <Layout
+           navbar={<Navbar logo={<b>Remit</b>} />}
+           pageMap={await getPageMap()}
+           footer={<Footer>Remit</Footer>}
+         >
+           {children}
+         </Layout>
+       </body>
+     </html>
+   )
+ }
```

Key changes:
- **`async` layout** — needed because `getPageMap()` is async
- **`suppressHydrationWarning`** — prevents React warnings from dark mode theme switching
- **`<Head />`** — Nextra's head component (handles meta, og tags, etc.)
- **`getPageMap()`** — scans the `app/` directory for `.mdx` files and builds the nav tree automatically

---

## 6. Delete `app/page.tsx`, Add `.mdx` Pages

The default `page.tsx` was deleted. Nextra works with MDX files, so pages become `.mdx`:

```
app/
├── page.mdx                    # Home page (/)
├── getting-started/
│   └── page.mdx               # /getting-started
├── guide/
│   └── page.mdx               # /guide
└── others/
    └── setup-nextra.mdx       # /others/setup-nextra (this file!)
```

Each MDX page starts with a `# Heading` which Nextra uses as the page title in the sidebar automatically:

```mdx
# Getting Started

Welcome to the getting started guide.
```

## 7. The Bug: Zod v4 `nonoptional` Error

After running `bun dev`, the site crashed immediately with a 500 error:

```
⨯ Error: ✖ Invalid input: expected nonoptional, received undefined
  → at children
  digest: '1872370934'
```

### What caused it

Nextra 4.6.1's `Layout` component validates its props using a strict Zod schema (`LayoutPropsSchema`). The schema defines `children` as a **required** field:

```ts
// nextra-theme-docs/dist/schemas.js
const LayoutPropsSchema = z.strictObject({
  children: reactNode,   // ← required, NOT optional
  navbar: reactNode.optional(),
  footer: reactNode.optional(),
  // ...
})
```

However, the compiled `layout.js` destructures `children` out of the props **before** calling `safeParse`, so `children` ends up missing from the object being validated:

```js
// nextra-theme-docs/dist/layout.js — the bug
const { children, ...themeConfig } = props   // children pulled out here
LayoutPropsSchema.safeParse(themeConfig)      // but NOT passed in → undefined!
```

In **Zod v3**, `z.custom()` silently accepted `undefined`. In **Zod v4**, `z.custom()` is nonoptional by default and throws on `undefined`. Since Nextra 4.6.1 ships with `zod ^4.1.12` as a dependency, using Zod 4 exposed this latent bug.

### The fix

A one-line patch to `nextra-theme-docs/dist/layout.js` — include `children` back in the object passed to `safeParse`:

```diff
- LayoutPropsSchema.safeParse(themeConfig)
+ LayoutPropsSchema.safeParse({ children, ...themeConfig })
```

After this patch, the server returned `GET / 200` and `GET /getting-started 200` cleanly.

> **Note:** This patch lives inside `node_modules` and will be lost after a fresh `bun install` or `npm install`.
> To persist it, use [`patch-package`](https://github.com/ds300/patch-package),
> or wait for an official Nextra fix release.

## 8. The Hydration Warning (Harmless)

After the fix, you may still see this in the terminal:

```
[browser] A tree hydrated but some attributes of the server rendered HTML didn't match...
  <body
-   cz-shortcut-listen="true"
  >
```

The `cz-shortcut-listen` attribute is injected by a **browser extension**. It is not part of your code and does not affect functionality. Safely ignore it.

## 9. Killing a Stuck Dev Server

If `bun dev` complains that port 3000 is already in use, use **PowerShell** (not Git Bash) to kill it:

```powershell
# Kill by PID
Stop-Process -Id 13020 -Force

# Or kill whatever is holding port 3000
Stop-Process -Id (Get-NetTCPConnection -LocalPort 3000).OwningProcess -Force
```

> **Git Bash gotcha:** Running `taskkill /PID 13020 /F` in Git Bash fails because Bash
> interprets `/PID` as a Unix file path (`C:/Program Files/Git/PID`). Always use
> PowerShell for Windows-native process commands.
